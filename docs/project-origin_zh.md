# 项目由来与问题背景

状态：v0 草案

CarMediaHub 起源于一个实际的自托管媒体问题：个人文件可能位于 NAS、本地硬盘或网盘，而车机浏览器往往受到编解码器、内存、CPU、网络和播放 API 的限制。文件管理页面可以展示文件，但在受限的车机环境中直接播放并不总是可靠。

因此，车机是 CarMediaHub 的重要客户端之一，但不是平台本身。平台提供统一入口、服务绑定、媒体处理和插件机制，把媒体来源适配为浏览器或车机能够稳定消费的形式。

## 典型媒体链路

```text
网盘 / NAS / 本地硬盘
        -> rclone WebDAV（需要统一上游时）
        -> AList WebDAV 或文件服务
        -> WDR 或其他媒体插件
        -> 切片 / 转封装 / 转码
        -> 浏览器或车机显示屏
```

rclone、AList、FFmpeg、7z、数据库以及可选的 Mihomo/Clash 服务属于平台管理或运营者管理的基础服务。它们可以运行在 Docker、宿主操作系统、WSL 或运营者控制的其他机器上，不要求修改这些项目的源代码。CarMediaHub 通过声明式服务绑定连接它们，并在运营者授权后通过网关发布相应入口。

WDR 是 CarMediaHub 自实现的媒体呈现插件。它可以消费 AList WebDAV，但不是 AList 的扩展，也不代表平台架构本身。它负责扫描和呈现媒体，根据客户端能力选择传输策略，并在直播放不稳定时使用切片或转码。

## 两类插件

### 自实现插件

自实现插件实现 CarMediaHub 特定的业务流程。WDR 是一个例子：它通过平台能力和服务绑定，将运营者控制的媒体转换为适合受限客户端的播放体验。

### 代理与兼容插件

代理插件在不修改上游项目源代码的前提下，把已有 Web 服务或网站接入网关。它们可能需要持续维护站点特有的认证、重定向、Cookie、WebSocket/SSE、资源路径、流式传输或反自动化行为。

例如 AList Web、Clash Web 或其他运营者控制的内网服务，都可以通过兼容层挂载到 CarMediaHub 的逻辑路径。代理插件不是上游应用本身，而是负责让上游服务能够通过 CarMediaHub 使用的适配器。

部分适配器会使用运营者明确授权的浏览器会话或配置好的网络出口。平台不提供无限制的公共代理服务，用户仍需自行承担授权、内容权利、上游服务条款和适用法律责任。

## 为什么需要平台

早期方案也探索过远程浏览器和远程桌面，但交互延迟和资源消耗不适合车机显示。网关与插件模型让界面更接近客户端，同时把认证、兼容处理、媒体处理和资源控制放在运营者自己的基础设施上。

CarMediaHub 不局限于一种媒体工作流。长期目标是让用户能够开发或安装自己的适配器，并复用 Core 提供的身份、语言与格式化、服务绑定、秘密、存储、媒体任务、历史、路由、诊断和运行时隔离能力。

## 责任边界

CarMediaHub 提供框架、SDK 契约、网关和能力控制。运营者决定接入哪些服务、域名、网络路径、存储和上游账号。插件维护者负责目标服务的兼容性，并声明所需能力和数据流。
