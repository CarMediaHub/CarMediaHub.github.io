# 基础服务与服务绑定

状态：v0 草案

CarMediaHub 将媒体和网络工具视为由运营者控制的基础服务。服务可以与 Core 部署在同一主机，也可以由运营者管理的其他主机提供；插件通过受控的服务绑定访问它们，不为每个插件单独开放公网端口。

## 基础服务角色

- **AList**：为运营者管理的存储提供文件目录和 WebDAV 能力。
- **rclone**：挂载或统一不同存储提供商，并为兼容服务提供受控的 WebDAV 端点。
- **FFmpeg**：为媒体探测、封装转换以及后续播放流水线提供处理能力。
- **Mihomo** 及同类网络工具：由运营者自行管理的网络服务，Core 不预设路由策略。
- **Nginx 或等价网关**：可以用于路由内部组件流量，但不是每种部署都必须使用，也不会要求每个插件占用一个公网端口。

这些服务属于兼容目标和受管依赖。CarMediaHub 不修改上游源码；兼容插件通过 Core 的服务绑定 API 适配它们，使客户端能够从统一入口使用相关能力。

## 绑定模型

运营者可以为某个已安装的插件实例配置绑定。绑定包含服务标识和内部上游地址，并由 Core 统一施加健康检查、请求和响应大小限制、并发限制以及重定向限制。插件拿到的是受能力范围约束的客户端，不会拿到原始数据库连接、任意命令执行能力、宿主环境变量或不受限制的网络套接字。

绑定不是自动发现机制。Core 不扫描局域网，不从 `PATH` 推断服务位置，也不会隐式读取系统环境变量。运营者需要通过管理端或部署配置显式提供服务端点和凭据；密钥始终处于 Core 管理的凭据边界内。

## 典型媒体链路

```text
浏览器或车机客户端
  -> CarMediaHub 单一入口
  -> 插件路由
  -> 受控服务绑定
  -> 运营者管理的 AList/rclone/媒体服务
```

未来可以增加受管的 FFmpeg Worker 或 Native/Docker 服务运行器，但这些属于独立发布门槛。当前绑定契约不表示真实 FFmpeg 转码、HLS 封装，或所有平台上的 AList/rclone/Mihomo 二进制已经随项目发布。

## 运营边界

- 绑定作用域限定为一个安装实例和一个插件实例。
- 健康检查必须使用明确的安全端点；重定向和响应大小受到限制。
- 绑定失败以稳定诊断码反馈，不向客户端暴露上游路径或密钥。
- 运营者负责上游服务的许可、凭据、网络策略、存储权限和安全维护。
- 必需绑定不可用时，插件必须给出清晰的降级状态。

## 当前状态

Core 的服务绑定 API、安装实例隔离、健康检查、请求/响应/并发限制和管理端表示已经实现并通过测试。真实第三方二进制的 Native/Docker 分发、平台级恢复以及生产级媒体流水线仍属于计划工作，具体门槛以治理仓库总计划为准。
