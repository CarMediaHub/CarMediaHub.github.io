# 프로젝트 유래와 문제 배경

상태: v0 초안

CarMediaHub는 실제 자체 호스팅 미디어 문제에서 출발했습니다. 개인 파일은 NAS, 로컬 디스크 또는 클라우드 드라이브에 있을 수 있지만 차량용 브라우저는 코덱, 메모리, CPU, 네트워크와 재생 API에 제약이 있습니다. 파일 관리 화면에서 파일을 보여 주는 것과 제한된 차량 환경에서 안정적으로 재생하는 것은 다른 문제입니다.

따라서 차량용 화면은 중요한 클라이언트이지만 플랫폼 자체는 아닙니다. 플랫폼은 하나의 진입점, 서비스 바인딩, 미디어 처리와 플러그인을 제공하여 미디어 소스를 브라우저나 차량용 화면이 처리할 수 있는 형태로 변환합니다.

## 일반적인 미디어 경로

```text
클라우드 드라이브 / NAS / 로컬 디스크
        -> rclone WebDAV (상류 연결을 정규화할 때)
        -> AList WebDAV 또는 파일 서비스
        -> WDR 또는 다른 미디어 플러그인
        -> 분할 / 리먹스 / 트랜스코딩
        -> 브라우저 또는 차량용 화면
```

rclone, AList, FFmpeg, 7z, 데이터베이스와 선택적 Mihomo/Clash 서비스는 플랫폼 또는 운영자가 관리하는 기반 서비스입니다. Docker, 호스트 OS, WSL 또는 운영자가 관리하는 다른 컴퓨터에서 실행할 수 있으며, 해당 프로젝트의 소스 코드를 수정할 필요가 없습니다. CarMediaHub는 선언된 서비스 바인딩으로 연결하고 운영자가 승인한 경로만 게이트웨이를 통해 노출합니다.

WDR은 CarMediaHub가 직접 구현하는 미디어 표시 플러그인입니다. AList WebDAV를 사용할 수 있지만 AList의 확장이 아니며 플랫폼 아키텍처 자체도 아닙니다. WDR은 미디어를 검색하고 표시하며 클라이언트 능력에 맞는 전송 방식을 선택하고 직접 재생이 불안정할 때 분할 또는 트랜스코딩을 사용합니다.

## 두 가지 플러그인 계열

### 네이티브 플러그인

네이티브 플러그인은 CarMediaHub 전용 업무 흐름을 구현합니다. WDR은 운영자가 관리하는 미디어를 제한된 클라이언트에 맞는 재생 경험으로 바꾸는 예입니다.

### 프록시 및 호환성 플러그인

프록시 플러그인은 상류 프로젝트의 소스 코드를 수정하지 않고 기존 웹 서비스나 웹사이트를 게이트웨이에 연결합니다. 인증, 리디렉션, 쿠키, WebSocket/SSE, 리소스 경로, 스트리밍 및 자동화 방어와 같은 대상별 동작을 지속적으로 유지해야 할 수 있습니다.

AList Web, Clash Web 또는 운영자가 관리하는 다른 내부 서비스도 호환성 계층을 통해 CarMediaHub 논리 경로에 연결할 수 있습니다. 프록시 플러그인은 상류 애플리케이션 자체가 아니라 CarMediaHub에서 사용할 수 있도록 유지되는 어댑터입니다.

일부 어댑터는 운영자가 명시적으로 승인한 브라우저 세션이나 설정된 네트워크 출구를 사용합니다. 플랫폼은 무제한 공용 프록시 서비스를 제공하지 않으며, 사용자는 권한, 콘텐츠 권리, 상류 서비스 약관과 적용 법률을 책임집니다.

## 플랫폼이 필요한 이유

초기에는 원격 브라우저와 원격 데스크톱도 검토했지만 상호작용 지연과 자원 사용량이 차량용 화면에 적합하지 않았습니다. 게이트웨이와 플러그인 모델은 클라이언트에 가까운 화면을 유지하면서 인증, 호환성 처리, 미디어 처리와 자원 제어를 운영자 인프라에서 수행합니다.

CarMediaHub의 장기 목표는 하나의 미디어 흐름에 한정되지 않습니다. 사용자가 자신의 어댑터를 개발하거나 설치하고, Core의 ID, 언어 및 형식화, 서비스 바인딩, 비밀 저장소, 스토리지, 미디어 작업, 기록, 라우팅, 진단과 런타임 격리를 공유하도록 하는 것이 목표입니다.

## 책임 경계

CarMediaHub는 프레임워크, SDK 계약, 게이트웨이와 capability 제어를 제공합니다. 운영자는 연결할 서비스, 도메인, 네트워크 경로, 저장소와 상류 계정을 선택합니다. 플러그인 유지 관리자는 대상 서비스 호환성과 필요한 capability 및 데이터 흐름을 선언할 책임이 있습니다.
